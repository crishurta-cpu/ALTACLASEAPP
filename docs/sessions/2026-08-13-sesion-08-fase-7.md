## 🔑 Decisiones de diseño (desviaciones del plan original)

1. **`NuevoMovimiento.jsx` NO se creó.** Es el orquestador de tabs (Ingreso/Lote/Gasto) y todavía envuelve `GastoForm`, que pertenece a Fase 8. Moverlo crearía una dependencia cruzada. `App.jsx` sigue siendo el dueño de `NuevoMovimiento` y los 3 formularios de ingresos se importan individualmente con paths explícitos. Cuando Fase 8 cree `features/gastos/`, se evaluará si conviene mover `NuevoMovimiento` a un shell compartido (`app/AddSheet.jsx`?) o mantenerlo en `App.jsx`.

2. **`useIngresoForm.js` NO se creó.** La lógica de `useState` está acoplada al JSX del formulario. Refactorizar a hook sin un consumidor real (Fase 16 con Context API podría beneficiarlo) sería abstracción prematura. Se reservó la carpeta `hooks/` vacía para futuro uso.

3. **`IngresoBloqueForm` pasa `onSave(item)` con shape de negocio** (no fila Sheets). Mantiene el comportamiento original donde cada fila del lote se transforma y guarda individualmente. Si en Fase 19 se centraliza la transformación en un servicio, este componente también cambiará.

4. **Imports con paths explícitos** (no del barrel) en `App.jsx`. Mismo patrón que Fases 5–6: cuando haya 3+ features en `shared/ui/`, `shared/charts/`, etc., se migrará a barrels.
